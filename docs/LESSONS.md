# 开发中的问题与解决

本文收集 Tickbird 开发中每一次「发现问题 → 弄清原因 → 解决」的经过。
每条场景写明现象、发现方式、原因、解决、经验和出处。
先读「通用规律」，再按主题查具体场景。
遇到类似问题时，先搜关键词（如 `$PPID`、DA1、hook 信任）。
本文随开发持续更新，每一步端到端测试后补充。

出处说明：提交号指本仓库的提交；`DEVELOPMENT_LOG` 和 `archived/` 是只在本地的开发记录；「记忆」指开发助手的实测笔记。

## 通用规律

1. **先实测，再相信文档和旧结论。** Agent 的行为随版本变化，文档常常没写。旧结论也会被新版本推翻。见场景 1、9、10、15、16、17、21、27。
2. **环境变量和父进程可能是继承来的，要核实。** 进程「在哪里」不能只看变量。见场景 21、36、37、74。
3. **不确定就不做，绝不做错。** 宁可不开栏、不合并、不显示，也不开到别的窗口旁边、合错内容。见场景 25、36、58、60。
4. **只用来源里的事实，不推测。** 退出码、行号、成功与否，记录里没有就不编。见场景 45、62、63、64。
5. **优先读 Agent 自己发布的状态。** 它比按文件时间猜可靠。见场景 13、14、16、66、102。
6. **事件的先后和到达时间都不可信。** 后台 hook 会乱序，终端回答会晚到。按时间戳排序，按标记判断结束。见场景 11、30、31。
7. **等一个回答时，用结束标记，超时只兜底。** 见场景 29、30。
8. **分清每层测试能证明什么。** 单测、浏览器替身、合成宿主各证明一层，不能互相代替。「总绿」也可能掩盖中途失败。见场景 50、52、78、84。
9. **先复现，再修。** 用修复前的代码跑一遍新检查，确认它能抓到问题。见场景 50、51、72。
10. **按版本缓存的东西，改了就升版本。** 见场景 80、89、90。
11. **工具的「成功」和「无输出」不一定可信。** 静默跳过、静默退出、对不存在的对象报成功，都要另行核对。见场景 7、81、91。
12. **Tickbird 不能挡 Agent 的路。** hook 静默、快速、绝不失败；任何情况都不往 Agent 输入。见场景 2、8、18。
13. **向交互程序输入前，先读屏幕。** 见场景 83、86。
14. **用户说「去掉」就是删掉。** 反馈针对的是结构和占地，不是颜色深浅。见场景 97、100。

## Agent 行为与 hook

### 1. 命令型 hook 的 `$PPID` 是 Agent 进程
- **现象**：hook 需要知道自己属于哪个 Agent 进程、哪个窗口。
- **发现方式**：终端原型实测，Claude Code 2.1.289、Codex 0.160.0。
- **原因**：命令型 hook 跑在 shell 里，父进程就是 `claude` 或 `codex`，并继承终端的环境变量（含 `KITTY_WINDOW_ID`）。在 VS Code 里，再上一级是窗口的扩展宿主。
- **解决**：状态文件记录 `agentPid`（`$PPID`）和 `hostPid`（它的父进程）。VS Code 版用自己的 `process.pid` 认出本窗口的会话，两个窗口开同一文件夹也能区分。
- **经验**：这条在 Codex 0.157 起的共用后台下不成立，见场景 21。进程关系要按 Agent 的运行方式分别核实。
- **出处**：a3a65e4、`terminal-prototype:DEVELOPMENT_STATUS.md`；记忆 terminal-sidecar-hooks；2026-10-05。

### 2. SessionStart 的 stdout 会进入模型上下文
- **现象**：hook 打印的任何东西都会被模型读到。
- **发现方式**：终端原型实测。
- **原因**：SessionStart hook 的输出按设计会注入上下文。
- **解决**：hook 完全静默，决定写进日志（`~/.local/state/tickbird/hook.log`，后来是 `split.log`）。hook 捕获所有异常，日志失败也不影响 Agent。
- **经验**：给 Agent 写 hook，先查清它的输出去哪。观察工具不能改变被观察者。
- **出处**：a3a65e4；`plugins/tickbird-state/scripts/hook.mjs`、`plugins/tickbird-split/scripts/split.mjs` 注释；记忆 terminal-sidecar-hooks。

### 3. Claude Code 的会话记录在第一条消息后才出现
- **现象**：会话开始时，`transcript_path` 指向的文件还不存在。
- **发现方式**：终端原型实测。
- **原因**：Claude Code 在第一条消息后才创建会话记录。
- **解决**：栏先显示「等第一条消息」，等文件出现。VS Code 版只跟随「会话记录已写出」的会话。
- **经验**：hook 给的路径只是「将来会在这里」，读之前要检查存在。
- **出处**：a3a65e4；b6f1cc0；`tests/extension-state.test.ts`；C2-4 审阅截图「/clear 后：新会话还没有记录」。

### 4. `/clear` 是一次结束加一次开始
- **现象**：`/clear` 后会话 ID 变了，旧的绑定失效。
- **发现方式**：终端原型实测。
- **原因**：Claude Code 的 `/clear` 依次触发 SessionEnd（`clear`）和 SessionStart（`clear`），产生新会话。
- **解决**：原型在 SessionStart 时改绑同一栏。正式版改成按 Agent 进程绑定，见场景 46。
- **经验**：「会话」和「进程」是两回事，一个进程可以先后有多个会话。
- **出处**：a3a65e4；记忆 terminal-sidecar-hooks；2026-10-05。

### 5. Codex 的会话从第一条消息开始
- **现象**：Codex 启动时不触发 SessionStart；打开后不发消息就退出，只触发 SessionEnd，留下孤立的状态文件。
- **发现方式**：原型实测；私有安装时真实使用发现孤立文件。
- **原因**：Codex 在第一条消息时才开始会话，但退出时仍发 SessionEnd。
- **解决**：只有 `start` 事件能新建状态文件，其它事件遇到没有文件就丢弃。栏在 Codex 发出第一条消息时才出现。
- **经验**：不要假设事件成对出现。写入端要能承受「只有结束、没有开始」。
- **出处**：65ad932；`hook.mjs` 注释；C2-4 结果表「第一条消息时」。

### 6. Codex 也读插件里的 `hooks/hooks.json`
- **现象**：一个目录同时做 Claude Code 和 Codex 插件时，hook 定义会冲突。
- **发现方式**：原型实测。
- **原因**：Codex 除了自己的清单，也会读 `hooks/hooks.json`；Claude 格式的 hook 放在那里会被 Codex 误读。
- **解决**：两边的 hook 都内联在各自的清单（`.claude-plugin/plugin.json`、`.codex-plugin/plugin.json`），共用一份脚本。
- **经验**：双平台插件要查清每个平台会读哪些默认路径。
- **出处**：a3a65e4；记忆 terminal-sidecar-hooks。

### 7. Codex 的 hook 必须先信任，否则静默跳过
- **现象**：装好插件，Codex 的 hook 却一个都没执行，也没有报错。
- **发现方式**：VS Code 里的 Codex 实测。
- **原因**：非托管 hook 要在 `/hooks` 里信任一次。信任按「插件 ID、事件、hook 定义的哈希」记在 `~/.codex/config.toml`。`--dangerously-bypass-hook-trust` 只对 `codex exec` 有效，对 VS Code 启动的 app-server 无效。
- **解决**：安装脚本提示去 `/hooks` 按 `t` 信任。显示端发现「Codex 会话没有状态文件」时提示一次。插件改名、hook 命令行改了要重新信任；只改脚本内容不用。测试结束后删掉测试留下的信任记录。
- **经验**：静默跳过是最难查的失败。安装流程要主动引导，显示端要能发现「本该有却没有」。
- **出处**：记忆 terminal-sidecar-hooks、sidecar-private-install；`docs/SESSION_STATE.md`「启用与停用」；`DEVELOPMENT_LOG` B2、B3；2026-10-05。

### 8. hook 的超时有上限
- **现象**：清单里写的超时不一定生效。
- **发现方式**：私有安装时发现。
- **原因**：Codex 把 `SessionEnd`、`Interrupt` 的 hook 超时限制在 3 秒；Claude Code 的 SessionEnd 总预算 1.5 秒。
- **解决**：清单按上限设置。hook 只追加一行、不联网、不读会话记录。
- **经验**：结束类 hook 要按最紧的预算设计。
- **出处**：65ad932；记忆 terminal-sidecar-hooks、sidecar-private-install。

### 9. 「等你批准」不在会话记录里
- **现象**：Agent 停在批准提示时，会话记录没有任何变化，Tickbird 看起来像卡住。
- **发现方式**：hook 能力实测，对比 hook 输入与会话记录的写入时间。
- **原因**：`PermissionRequest`（两边都有）在调用写入后 0.05–0.09 秒触发，带工具名和参数。会话记录里没有这段状态。Claude 的 `Notification(permission_prompt)` 晚约 6 秒，只适合提醒。两个 Agent 都不通知「批准已处理」。
- **解决**：用 `PermissionRequest` 写 `approval` 事件。会话记录里出现批准之后的新记录，就算已处理（`awaitingApproval(state, 会话记录最后时间)`），不能只看 `phase`。
- **经验**：一个状态的开始和结束可能来自两个不同的来源，要分别找。
- **出处**：`terminal-prototype:DEVELOPMENT_STATUS.md`「hook 能力实测」；`docs/SESSION_STATE.md`；48bee3d；2026-10-05。

### 10. `MessageDisplay` 只能补长回答的延迟
- **现象**：Claude Code 屏幕上已经有字，会话记录里还没有。
- **发现方式**：hook 能力实测。
- **原因**：`MessageDisplay`（只有 Claude）约 0.5 秒一段流式送出，首段比会话记录早约 12 秒。调用前的短句只早 0.07 秒，因为 Claude Code 自己也等调用参数生成完才显示。Codex 没有对应事件。显示的 id 和记录的 id 对不上。
- **解决**：把分段记成 `display` 事件，显示端以暗淡（终端里加斜体）先显示。会话记录里出现同样开头的文字后，按内容去重丢弃。
- **经验**：先量清一个事件能补多少延迟，再决定做不做。id 对不上时，可以按内容去重。
- **出处**：`terminal-prototype:DEVELOPMENT_STATUS.md`；b6f1cc0；记忆 terminal-sidecar-hooks。

### 11. 后台 hook 的写入顺序会乱
- **现象**：最后一段显示文字晚于回合结束写入；显示事件的时间可能早于它之后的批准。
- **发现方式**：真实 Claude Code 2.1.289 端到端测试。
- **原因**：除开始和结束外，hook 都在后台执行（`async: true`），写入先后不等于发生先后。
- **解决**：折叠时按每行的 `t` 排序，流式文字按 `index` 拼接。`display` 不结束等待；空闲时不留 draft。每次只追加一短行，并发写入不会交错。
- **经验**：异步写入的日志要按自带时间戳重建顺序，并让状态机对迟到事件免疫。
- **出处**：48bee3d；`packages/core/src/session-state.ts` 注释；`tests/session-state.test.ts`。

### 12. 有些回合结束不触发 Stop
- **现象**：会话状态停在 working，直到下一条消息。
- **发现方式**：VS Code 版端到端测试。当时扩展自带的 codex 0.155 不支持配置里的模型，回合报错。
- **原因**：Codex 回合报错时不触发 `Stop`。另外 Claude Code 用 `-p` 运行时，后台的 `Stop` hook 可能来不及写入。
- **解决**：记为已知问题。显示以会话记录为准，不受影响。
- **经验**：hook 状态只是补充，内容的唯一来源仍是会话记录。
- **出处**：`DEVELOPMENT_LOG` B2；`docs/STATUS.md`「已知问题」。

### 13. 回应前按 Esc，会话记录里什么都不写
- **现象**：中断后 Tickbird 仍在计时，显示「暂未取得本轮过程」。
- **发现方式**：实时显示的使用中发现。
- **原因**：Claude Code 在回应前被中断时不写中断记录，只把提示放回输入框。重发的请求和前一条有同一个 `parentUuid`。
- **解决**：读 Claude Code 自己的 `~/.claude/sessions/<pid>.json`（`sessionId`、`busy`/`idle`），并校验进程存活；idle 时立即停止计时。同一父记录下再次提问时，把前一轮标为「回合中断」。
- **经验**：日志缺了一段时，找 Agent 发布的其它状态，不靠沉默时长猜。
- **出处**：`DEVELOPMENT_LOG` 2026-09-23（六）；`packages/core/src/agent-status.ts`；记忆 turn-semantics-cross-harness。

### 14. Claude Code 的进程状态文件也知道「等批准」
- **现象**：已经用 hook 判断等批准；是否还有别的来源？
- **发现方式**：2026-10-08 调研。
- **原因**：`~/.claude/sessions/<pid>.json` 是每个进程一份的内部文件，没有文档。它含 `sessionId`（`/clear` 后变）、`cwd`、`kind`、`entrypoint`、`status`（`idle`/`busy`/`waiting`）、`waitingFor`（如 `permission prompt`），甚至所在的 tmux 窗格。进程退出时删除。
- **解决**：记为备选。Claude 的等批准不装 hook 也能知道，代价是依赖一个内部文件。现在仍用 hook。
- **经验**：内部文件能力更强，但随时可能变。用之前想清楚退路。
- **出处**：`docs/TERMINAL_PLAN.md` C2-5「已核实」；2026-10-08 实测（Claude Code 2.1.293）。

### 15. Claude Code 写会话记录有固定的滞后
- **现象**：Tickbird 比 Claude Code 界面慢几秒。
- **发现方式**：监听本会话 JSONL 的写入时间。
- **原因**：调用记录在工具开始时写入（晚约 150ms），结果在结束时写入。但同一响应里调用前的思考和正文，要等调用参数生成完才一起写入，实测晚 1.1 秒、3.2 秒，长参数可达十几秒。Tickbird 自身每次更新 14–85ms。
- **解决**：不在 Tickbird 侧优化；用 `MessageDisplay` 补长回答（场景 10）。
- **经验**：先量清延迟在谁那里，再决定改哪里。
- **出处**：`DEVELOPMENT_LOG` 2026-09-23（五）；记忆 turn-semantics-cross-harness。

### 16. Claude 的轮次要推导，天真计数会错约 9 倍
- **现象**：按 `type:"user"` 数轮次，数字大得离谱。
- **发现方式**：2026-08-31 本机实测 64 个 Claude Code 会话、4 个 Codex 会话。
- **原因**：Claude Code 没有原生轮次边界。`user` 记录里 88.5% 是 `tool_result`，只有 9.4% 是真实提问。Codex 有原生边界，但也有既未完成也未中止的悬空轮次。
- **解决**：过滤后推导轮次。Claude 的 `system/turn_duration` 作为回合结束边界并带原生时长。
- **经验**：跨平台统计前，先确认每个平台的「单位」是什么。
- **出处**：记忆 turn-semantics-cross-harness；`DEVELOPMENT_LOG` 2026-09-23（二）。

### 17. Claude 的思考摘要开始有正文
- **现象**：用户说 Tickbird 里「中间的对话丢了」。
- **发现方式**：用户反馈，再查会话记录。
- **原因**：Claude Code 2.1.280 起间歇写入思考摘要，并在界面上显示。解析器沿用旧结论，把 `thinking` 一律当隐藏推理。同版本别的会话也可能全空。
- **解决**：有正文就显示为「思考摘要」，签名和 `redacted_thinking` 仍排除。Codex 的 `reasoning.summary` 同样显示。
- **经验**：旧结论（「两边都拿不到思考正文」）要随版本复查。规则写成「有则显示」。
- **出处**：`DEVELOPMENT_LOG` 2026-09-23（二）；记忆 turn-semantics-cross-harness（「2026-09-23 已推翻」）。

### 18. 不订阅 PostToolUse
- **现象**：等批准的结束点本可以用 `PostToolUse` 判断。
- **发现方式**：会话状态设计时权衡。
- **原因**：每次工具调用都多一次同步 hook，拖慢 Agent。
- **解决**：不订阅；用会话记录判断批准已处理（场景 9）。
- **经验**：观察工具的代价要算在被观察者身上。
- **出处**：`docs/SESSION_STATE.md`「位置」；48bee3d。

### 19. VS Code 里的 Agent 也会执行 hook
- **现象**：不确定 VS Code 扩展里的对话是否会触发用户级和插件 hook。
- **发现方式**：隔离 VS Code + 项目级探针 hook 实测。
- **原因**：Claude Code 扩展用 SDK 启动 claude，`settingSources: ["user","project","local"]`。打开面板即触发 SessionStart（还没发消息），关窗触发 SessionEnd（`other`）。Codex 信任后也完整触发，进程链是 hook → app-server → 窗口扩展宿主。
- **解决**：VS Code 版和终端版共用一个状态插件。
- **经验**：同一个 Agent 在不同宿主里的触发时机不同（Claude 在 VS Code 里打开即开始，在终端里要等消息才有记录）。
- **出处**：`terminal-prototype:DEVELOPMENT_STATUS.md`；记忆 terminal-sidecar-hooks；2026-10-05。

### 20. `claude --bg` 的会话没有可开栏的终端
- **现象**：后台会话不在任何窗格里。
- **发现方式**：2026-10-08 调研。
- **原因**：`--bg` 会话运行在 `claude daemon run` 下，每个会话一个 `bg-pty-host`（自己的虚拟终端）。仍是一个会话一个进程。
- **解决**：暂不支持，不开栏。
- **经验**：同一个 Agent 有多种运行结构，适配前先列出来。
- **出处**：`docs/TERMINAL_DESIGN.md` 第 9 节「两层适配」表；2026-10-08 C2-4 端到端实测。

## Codex 共用后台

### 21. Codex 0.157 起，hook 的父进程是共用后台
- **现象**：Codex 的栏开不出来，或日志里的 kitty 窗口不对。
- **发现方式**：C2-4 端到端测试。
- **原因**：Codex 0.157+ 在共用的 app-server 后台里运行所有 hook：一个监管进程（`codex app-server daemon pid-update-loop`）加一个工作进程（`codex app-server --listen unix:// --managed-daemon`）。`$PPID` 是后台。后台的环境变量来自第一个启动它的终端，和当前窗格无关。
- **解决**：增加 Agent 层 `front.mjs`：识别到后台时，找终端里的 `codex` 前台，读前台的环境变量（macOS `ps -E`，Linux `/proc/<pid>/environ`）。`tickbird-state` 把前台记为 `agentPid`，另记 `serverPid` 供排查。berthd、cmux、openrig 等工具也遇到了同样的问题。
- **经验**：hook 在哪个进程里运行，决定了它知道什么。场景 1 的结论要按运行方式重新核实。
- **出处**：89c63fa；`docs/TERMINAL_PLAN.md` C2-4 结果；`docs/TERMINAL_DESIGN.md` 第 9 节；2026-10-08。

### 22. 共用后台不随会话退出
- **现象**：用后台进程判断会话结束，栏永远不关。
- **发现方式**：C2-4 调研与测试。
- **原因**：后台常驻不退出；Codex 自动升级时，工作进程的 pid 会变。
- **解决**：栏绑定终端里的前台。`/quit` 或 `kill -9` 前台后，栏在 2 秒内关闭，后台仍在。
- **经验**：绑定对象要和用户感知的生命周期一致。
- **出处**：89c63fa；`docs/TERMINAL_DESIGN.md` 第 9 节；C2-4 审阅表；2026-10-08 C2-4 端到端实测（本机进程列表与 `codex app-server daemon` 命令）。

### 23. 带 `-c` 等参数时 Codex 不用共用后台
- **现象**：用 `codex -c 'hooks.SessionStart=[…]'` 临时传 hook 测试，测不到共用后台的行为。
- **发现方式**：C2-4 测试。
- **原因**：任何 `-c`、`--enable`、`--disable`、`--search` 或 `--no-daemon` 都让 Codex 以 embedded 方式运行。
- **解决**：两种方式都测。测共用后台时，用单独的 `CODEX_HOME` 和其中的 `hooks.json`，后台从没有终端的 shell 启动，保证环境变量与任何窗格无关。
- **经验**：测试手段本身可能改变被测对象的运行方式。
- **出处**：`plugins/tickbird-split/README.md`「本地试用」；C2-4 审阅页说明；2026-10-08 C2-4 端到端实测（本机进程列表与 `codex app-server daemon` 命令）。

### 24. 协议里没有「哪个客户端拥有这个会话」
- **现象**：想直接问 app-server「这个会话显示在哪个终端」。
- **发现方式**：C2-4 调研 app-server JSON-RPC 协议。
- **原因**：协议没有这个字段。批准是服务器发给客户端的请求，只有前台 TUI 会被问到。
- **解决**：从进程侧找前台：同目录、有终端的 `codex` 进程（macOS 用 `lsof` 取目录）。
- **经验**：协议给不了的信息，换一个可观察的侧面去拿。
- **出处**：`docs/TERMINAL_DESIGN.md` 第 9 节；2026-10-08 生成协议结构（`codex app-server generate-json-schema`）核对。

### 25. `/new` 不结束旧会话，按终端最近输入区分前台
- **现象**：同一目录开着两个 Codex，栏可能开到另一个旁边。
- **发现方式**：C2-4 端到端测试。
- **原因**：曾想用「前台已有别的会话」来排除。但 Codex 的 `/new` 不触发 SessionEnd，旧会话还在，这条规则分不清。
- **解决**：取终端设备的访问时间（`w` 的空闲时间也用它），即最近收到输入的终端。它必须在 30 秒内，且比第二个早至少 2 秒，否则不开栏，原因写进日志。
- **经验**：找一个和「刚发出消息」直接相关的信号。分不清时宁可不做。
- **出处**：89c63fa；`docs/TERMINAL_PLAN.md` C2-4；`plugins/tickbird-state/scripts/front.mjs`；C2-4 审阅表「同一目录两个 Codex」。

### 26. 自定义 `CODEX_HOME` 时栏找不到会话记录
- **现象**：测共用后台时，栏一直等不到内容。
- **发现方式**：C2-4 端到端测试。
- **原因**：栏只在默认目录找会话记录。
- **解决**：栏按状态文件里的 `transcript` 打开。
- **经验**：hook 已经给出的路径，下游直接用，不要重新推导。
- **出处**：89c63fa；`docs/TERMINAL_PLAN.md` C2-4。

### 27. 外部程序能读 Codex 后台的线程状态
- **现象**：Codex 的等批准能否像 Claude 那样，不用 hook 从 Agent 侧读到？
- **发现方式**：2026-10-08 调研协议，并做只读探测。
- **原因**：协议里线程状态 `active` 带 `activeFlags`：`waitingOnApproval`、`waitingOnUserInput`。第一次用 `codex app-server proxy` 探测没有回答：它只转发原始字节，而控制 socket 说的是 WebSocket（`GET /rpc`）。自己做 WebSocket 握手后，只调用 `initialize`、`thread/loaded/list`、`thread/read`，就读到了每个已加载线程的状态，并看到 `idle` → `active` 的变化。
- **解决**：读状态已证实；等批准时是否出现 `waitingOnApproval` 还没测到（Codex 用量到达上限，测试中断）。列入 C2-5 待核实，现在仍用 `PermissionRequest` hook。
- **经验**：探测没回答，先查传输层再下结论。协议里有字段，不等于实际会出现，要测到具体状态。
- **出处**：`docs/TERMINAL_PLAN.md` C2-5「已核实」「待核实」；2026-10-08 实测。

### 29. 没有回答也是回答：以 DA1 结束
- **现象**：tmux 不回答 DECRQM 2026（防闪烁）等查询。
- **发现方式**：C2-1 端到端测试。
- **原因**：不支持的终端直接不回答，单靠超时既慢又不准。每个终端都回答 DA1。
- **解决**：所有查询后跟一个 DA1。DA1 先回答而某项没回答，就是不支持。不按终端名字判断，XTVERSION 只进报告。
- **经验**：给一批查询加一个必有回答的结束标记。

### 30. kitty 窗口在后台时 DA1 晚约 190ms
- **现象**：符号偶尔退成 ASCII。
- **发现方式**：C2-2 端到端测试。
- **原因**：kitty 窗口在后台时回答要约 190ms，超过了 150ms 的探测限时，符号宽度量不到。

- **经验**：超时值要在最慢的真实场景下量，不要只在前台窗口里量。
- **出处**：3930446；`docs/TERMINAL_PLAN.md` C2-2；`caps.ts` 注释；2026-10-06。

### 31. 晚到的终端回答不能当按键
- **现象**：探测之后才到的回答，会被读成一串按键。

- **原因**：OSC、DCS、APC 回答可能在探测结束后才到。
- **解决**：输入解析把晚到的回答整段跳过。
- **经验**：输入流里混着终端回答，解析器要认得它们。

### 32. `TERM=dumb` 时什么都不发

- **发现方式**：C2-1 计划中的端到端测试。
- **原因**：哑终端不解释转义序列。
- **解决**：`TERM` 为空或 `dumb` 时不探测，全部按不支持。实测输出里没有 Esc 字节。

### 33. 符号宽度要实测

### 34. 会话记录里的文字不可信

### 35. kitty 远程控制的几个坑

### 36. 继承来的 `KITTY_WINDOW_ID`

## 终端版交互

### 46. 栏按 Agent 进程绑定，不按会话
- **现象**：原型用 SessionStart 改绑、SessionEnd 关栏，事件多、易漏。
- **发现方式**：C2-4 设计调整。
- **原因**：一个进程会先后有多个会话（场景 4、25）；进程被强杀时不发 SessionEnd。
- **解决**：插件只有一个 `SessionStart` hook，开栏后传 `watch --agent <pid>`。同一进程的新 `start` 让栏自己改绑；进程消失，栏 1 秒内退出。切回 Agent 的命令由插件用 `--focus` 传给栏，栏不认识终端。上下文压缩（`source: compact`）不开新栏。
- **经验**：绑定到生命周期最稳的那个对象，其它变化让下游自己跟。
- **出处**：89c63fa；`docs/TERMINAL_PLAN.md` C2-4「设计调整」；`split.mjs`。

### 47. 只读模式和一次性命令不开栏
- **现象**：`claude -p`、`codex exec` 也会触发 SessionStart。
- **发现方式**：C2-4 实现。
- **原因**：这些命令回答一次就退出。
- **解决**：识别 `-p`/`--print` 和 `exec`/`e`，不开栏。
- **经验**：先判断场景值不值得做，再做。
- **出处**：`plugins/tickbird-split/scripts/split.mjs`。

### 48. 详情统一成一种面板，按键统一成 vim / less
- **现象**：读文件、diff、命令各有一种排版；按键在各页意思不一致。
- **发现方式**：C2-3 审阅。
- **原因**：按内容类型分别设计，累积了不一致。
- **解决**：所有详情都是「左栏、竖线、正文」；左栏只有行号、`+` `-`、空白三种。能打开的调用行右端加暗淡的 `→`，选中时只改这一个标记。按键按 vim / less 习惯，同一个键在各页意思一致。
- **经验**：形式统一后，读者只学一次。
- **出处**：0cfefdb；`docs/TERMINAL_PLAN.md` C2-3「设计调整」；`docs/TERMINAL_DESIGN.md` 第 5、7 节。

## VS Code 宿主与 webview

### 49. Tickbird 被别的扩展打开的文件盖住
- **现象**：用户报告 Tickbird 偶尔被遮住。
- **发现方式**：用户反馈。
- **原因**：Tickbird 放在最左侧锁定的编辑器组里。别的扩展按「活动列」开文件时，会塞进这一组。维持这个组还要建组、锁组、调列宽。
- **解决**：改为左侧主侧栏的 WebviewView，详情在编辑器区打开。不再写任何编辑器组布局代码。宿主测试新增「文件按活动列打开时 Tickbird 仍可见」。Claude Code 和 Codex 都占右侧辅助侧栏，放左侧才能对照。
- **经验**：与宿主的布局机制对抗，代价会不断累积。换一个宿主原生支持的位置。
- **出处**：2fd11bc；`DEVELOPMENT_LOG` 2026-09-23；记忆 sidecar-host-placement；`tests/host/run.ts`。

### 50. 共存测试的「总绿」掩盖了中途失焦
- **现象**：真实 Agent 扩展共存测试在 CL1 失败；回查发现旧的「总绿」报告里，首次打开预览时也短暂失焦。
- **发现方式**：共存回归测试。
- **原因**：首次从两列展开三列时，公开布局命令把焦点转到中间组。旧报告只在末尾检查，焦点已恢复，所以没判失败。
- **解决**：等 `focusFirstEditorGroup` 完成后再建详情，只在 Tickbird 原本持有焦点的动作内恢复，不持续抢焦点。测试在每个关键阶段按 0/100/200ms 取样断言。
- **经验**：只看终态的测试会漏掉中间状态。关键阶段都要断言。

## 会话记录解析与展示

### 58. 子 Agent 日志混进会话列表并改写身份
- **现象**：出现「解析后的会话身份与候选不符」；主列表里有子 Agent 的日志。
- **发现方式**：用户指出「会话应该是某个 session」，现场排查。
- **原因**：主列表混入 5 份明确标记为 `subagent` 的 Codex 日志。它们继承的父 `session_meta` 又覆盖了子日志首条身份。
- **解决**：只排除来源明确声明 `subagent` 的日志，普通 fork 保留。解析固定首个会话身份；继承的元数据记覆盖记录和警告。
- **经验**：排除规则要基于明确声明，身份只认第一次出现。
- **出处**：`DEVELOPMENT_LOG`「Session／turn 粒度修正（2026-09-06）」。

### 59. 首条请求冒充会话标题
- **现象**：会话的大标题是第一条提问。
- **发现方式**：同上次用户反馈。
- **原因**：没有读会话的真实名称。
- **解决**：Claude 用同一会话的 `ai-title`，Codex 按精确 ID 读本地索引的 `thread_name`；都没有才回退首条请求。标题不参与绑定和活跃判断。
- **经验**：显示用的名字和身份分开，名字只用来读。
- **出处**：`DEVELOPMENT_LOG`「动作行与紧凑标题栏」；`archived/INFORMATION_ARCHITECTURE.md`。

### 60. 同一个提问显示两次
- **现象**：Codex 会话里两组提问各出现两次。
- **发现方式**：用户反馈，再核对来源行。
- **原因**：response 和 event 两路记录了相同正文，中间隔一条被排除的 developer 消息。旧的镜像条件要求物理行紧邻，所以漏合并。
- **解决**：只允许同一回合、相同正文、相反通道、跨一条已排除消息的合并。不做全局同文去重：两次相同的「同意」可能是两件事。正文合并不覆盖两路不同的图片字节。
- **经验**：去重规则要窄到只命中已证实的镜像。
- **出处**：`archived/UNSUPPORTED_CONTENT_AUDIT.md`「重复提问核对」；`DEVELOPMENT_LOG`「八项反馈」（2026-09-07）。

### 61. 内部推理被误列为「待支持」
- **现象**：盘点里有 61 条 Codex `event:agent_reasoning` 显示为待支持内容。
- **发现方式**：待支持内容盘点。
- **原因**：它和已排除的内部推理同类，却没被归到排除。
- **解决**：明确排除，只进覆盖记录，不生成节点，不推断「仍在思考」。
- **经验**：「不显示」要分清是「应排除」还是「待支持」，两者处理不同。
- **出处**：`archived/UNSUPPORTED_CONTENT_AUDIT.md`；2026-09-07。

### 62. 错误类别要有来源依据
- **现象**：样本里有 95 条非空 stderr，但 `tool_result.is_error` 只有 4 条；还有鉴权错误和权限规则拒绝混在普通文本里。
- **发现方式**：内容覆盖调查。
- **原因**：stderr 不等于失败，失败也不总有 stderr。
- **解决**：失败按来源区分（`exit N`、`failed`、`rejected`、`denied`、`interrupted`），退出码只取记录原值；单段检索 exit 1 标 `no match`。不因文本含 error 推断状态。
- **经验**：状态只从结构化字段取，不从文字猜。
- **出处**：`archived/CONTENT_DETAILS_DRAFT.md`；2fd11bc；`packages/core/src/model.ts` 注释。

### 63. 「可点」不等于「有返回」
- **现象**：想用 `availability` 区分「没返回、空返回、有返回」。
- **发现方式**：Action 展示复核。
- **原因**：`availability` 只表示有没有可读的详情增量。完整输入参数本身就能让一项可点。
- **解决**：adapter 显式标记结果：not-observed、empty、readable、unreadable、partial，独立于执行状态和可点性。
- **经验**：一个字段只表达一件事。复用字段表达别的含义，迟早出错。
- **出处**：`archived/ACTION_PRESENTATION_REVIEW.md`「数据事实」；`DEVELOPMENT_LOG`「窄版折叠试用」。

### 64. 图片的 MIME 声明和实际字节不一致
- **现象**：同一张图被当成两种格式，可能显示两次。
- **发现方式**：真实内容核对（`verify:content`）。
- **原因**：来源声明的 MIME 和 PNG 文件签名不一致；镜像记录又各声明一种。
- **解决**：按字节签名确定格式，按字节哈希去重，不改图片字节。
- **经验**：元数据和内容冲突时，信内容。
- **出处**：`archived/RENDER_VERIFICATION.md`「CX2 内嵌图片」；`scripts/verify-real-content.ts` 注释。

### 65. 「附带背景」里几乎全是噪音
- **现象**：附带背景里是空思考标记、运行附件、file-history-delta；用户粘贴的截图被归为「待核对：image」。
- **发现方式**：用户反馈与真实会话核对。

### 66. 读取被展示成 Bash

### 81. 隔离 VS Code 的数据目录路径不能太长
- **现象**：隔离 VS Code 启动失败，`code` 命令静默退出。
- **发现方式**：搭建隔离测试环境。
- **原因**：IPC socket 路径超过 103 字符。
- **解决**：`--user-data-dir` 用 `$TMPDIR` 下的短路径，不用临时工作区的长路径。
- **经验**：Unix socket 路径有长度上限，失败时常常没有提示。
- **出处**：记忆 terminal-sidecar-hooks。

### 82. VS Code 里的 Agent 对话无法自动发消息
- **现象**：想无人值守地在 VS Code 的 Agent 面板里发消息。
- **发现方式**：hook 实测。
- **原因**：Claude Code 扩展的 URI `/open?prompt=` 只填输入框，不发送。
- **解决**：Claude 侧由用户手动按发送。Codex 侧可用 `chatgpt.implementTodo({line,fileName,cwd,comment})` 自动发起任务。
- **经验**：自动化入口要实测「真的发出去了」。
- **出处**：记忆 terminal-sidecar-hooks；`terminal-prototype:DEVELOPMENT_STATUS.md`。

### 83. 界面控制不稳定时，不盲操作
- **现象**：控件树和截图停在旧画面；刚返回的命令框立即报失效。
- **发现方式**：真实 VS Code 人工验收时。
- **原因**：界面控制工具和窗口状态不同步。
- **解决**：不盲输命令，不重载正在运行的 Agent，不把菜单响应或旧画面计为通过或失败。同一阻塞连续三轮后标为受阻，等用户手动完成。
- **经验**：看不准屏幕时停下来。重复尝试有上限。
- **出处**：`DEVELOPMENT_LOG`「阻塞复查」「实机续验（2026-09-07）」。

### 84. 单测、编译、模拟演示都不能代替宿主验证
- **现象**：多次出现「测试全绿，但真实宿主里行为不同」的风险。
- **发现方式**：验证计划的制定与多轮验收。
- **原因**：每层测试只证明它那一层：浏览器替身不证明宿主焦点，合成日志不证明真实内容。
- **解决**：每次报告写明「不代表什么」。真实 VS Code 宿主测试（`test:host`）、真实 Agent 端到端测试单独列出。打包后的版本也跑一遍（`TICKBIRD_EXTENSION_PATH=build/vsix`）。
- **经验**：证据和结论的范围要对齐，部分通过就写部分通过。
- **出处**：`archived/VERIFICATION_PLAN.md`；`DEVELOPMENT_LOG`「当前证据」表；65ad932。

### 85. zsh 不对未加引号的 `$VAR` 分词
- **现象**：测试脚本里把一串参数放进变量再展开，命令收到的是一个整体参数。
- **发现方式**：C2-4 测试脚本，前后踩了两次。
- **原因**：zsh 默认不对 `$VAR` 做单词拆分，和 bash 不同。
- **解决**：用 `${=VAR}`，或写成函数。
- **经验**：测试脚本要按实际运行的 shell 写。
- **出处**：2026-10-08 C2-4 测试脚本中两次遇到。

### 86. 盲输进 TUI 撞上意外的提示
- **现象**：向 Agent 的 TUI 发送按键时，屏幕上恰好是一个更新提示，按键启动了 `brew upgrade`，及时停住。
- **发现方式**：C2-4 端到端测试。
- **原因**：TUI 当时的画面和预期不同。
- **解决**：每次发送输入前先读屏幕（`kitten @ get-text`），确认画面再发。
- **经验**：向交互程序输入前，先确认它在等什么。
- **出处**：2026-10-08 C2-4 端到端测试；C2-5 中再次遇到升级提示时先读屏幕，选了跳过。

### 87. 测试前检查用户级 hook
- **现象**：用户机器上有另一个工具留下的 hook，在 `~/.codex/hooks.json` 和 `~/.claude/settings.json` 里。
- **发现方式**：hook 实测时检查用户配置。
- **原因**：别的工具装过 hook 后没有清理。
- **解决**：按用户要求全部删除，含 Codex 的信任记录。之后两边都没有用户级 hook。
- **经验**：测 hook 前先看清环境里已有哪些 hook，否则结果会混在一起。
- **出处**：记忆 terminal-sidecar-hooks；2026-10-05。

## 安装、版本与分发

### 88. `.vsix` 不带 node_modules
- **现象**：打包要轻、可重复。
- **发现方式**：私有安装设计。
- **原因**：带依赖的包大且慢。
- **解决**：esbuild 打成单文件（4MB，大部分是 TypeScript 编译器），`.vsix` 1.2MB。hook 只用 Node 自带模块，不依赖仓库的 `node_modules`。
- **经验**：装到用户机器上的脚本，依赖越少越稳。
- **出处**：65ad932；`docs/SESSION_STATE.md`「约束」。

### 89. 插件按版本号缓存，改了不升版本就不更新
- **现象**：改了插件脚本，重装后行为不变。
- **发现方式**：私有安装实测。
- **原因**：Claude Code 和 Codex 都按插件 `version` 缓存已装的插件。
- **解决**：改插件目录里任何文件，都用 `npm run set-version` 升版本再安装。
- **经验**：遇到「改了没生效」，先查缓存的键。
- **出处**：65ad932；`plugins/tickbird-state/README.md`「版本」；记忆 sidecar-private-install。

### 90. 扩展和接入各有一个版本号
- **现象**：VS Code 扩展还在初始的 0.0.1，接入已到 0.1.2。
- **发现方式**：B3 整理。
- **原因**：两处各改各的，违背了「同一个版本号」的约定。
- **解决**：统一为 0.2.0。`npm run set-version -- x.y.z` 一次改 `package.json`、锁文件和插件清单；测试检查四处一致。
- **经验**：约定要用测试守住，不靠记忆。
- **出处**：1896b91；`tests/versions.test.ts`。

### 91. Codex 改名后旧市场看起来像新名字
- **现象**：市场改名后，列表里旧条目显示成新名字；删除不存在的插件也报成功。
- **发现方式**：插件拆分与改名时的安装脚本。
- **原因**：Codex 按清单里的名字列市场，不按登记时的键。`codex plugin remove` 对不存在的插件也返回成功。
- **解决**：安装脚本直接尝试删除旧名字的扩展、插件和市场，然后重新读取核对，不信删除命令的返回值。
- **经验**：显示名和键不同的系统里，改名要按键清理，并事后核对。
- **出处**：8367eff；`scripts/install-vscode.mjs` 注释；记忆 sidecar-private-install。

### 92. 两个插件各带一份 `front.mjs`
- **现象**：`tickbird-state` 和 `tickbird-split` 都需要「找前台」的逻辑。
- **发现方式**：C2-4 实现。
- **原因**：两个插件分开安装，不能互相引用。
- **解决**：两边各放一份相同的文件，测试检查两份一致。
- **经验**：不能共享时，复制加一致性测试。
- **出处**：89c63fa；两个插件的 README。

### 93. 插件按功能拆，不按产品拆
- **现象**：会话状态两个产品都要，自动分屏只有终端版要。
- **发现方式**：插件设计，用户确认方案 C。
- **原因**：按产品拆会重复，合在一起又不能单独停用分屏。
- **解决**：`tickbird-state`（共用）和 `tickbird-split`（终端版）。不想自动分屏，就在 Agent 的插件管理里停用它。
- **经验**：拆分边界放在用户想单独开关的地方。
- **出处**：8367eff；`DEVELOPMENT_LOG`「插件拆分与改名」。

### 94. 用户的 Agent 扩展落后
- **现象**：VS Code 里的 Codex 报 400，用不了新模型。
- **发现方式**：B3 整理时检查用户环境。
- **原因**：扩展自带的 codex 还是 0.155。
- **解决**：把 Codex、codex-audio、Claude Code 扩展升到当时的新版。
- **经验**：排查 Agent 行为前，先确认它的版本。
- **出处**：`DEVELOPMENT_LOG`「B3 整理」；记忆 sidecar-private-install。

### 95. 开发日志里有本机路径和真实会话 ID
- **现象**：开发日志要进共享仓库。
- **发现方式**：整理文档时。
- **原因**：日志记录了本地路径、真实会话 ID 和逐批测试细节。
- **解决**：日志移到 `local/`，不再跟踪；过期方案移到 `local/archived/`。`docs/` 只放共享文档。
- **经验**：分享前先过一遍隐私。日志和文档分开放。
- **出处**：3a93f87。

### 96. 测试 Codex 插件要改用户配置
- **现象**：Codex 装本地插件必须先加插件市场，会改用户配置。
- **发现方式**：终端原型。
- **原因**：Codex 没有「只在本次加载插件目录」的方式。
- **解决**：原型阶段用 `codex -c 'hooks.SessionStart=[…]'` 临时传入；正式安装统一走安装脚本（注意场景 23 的副作用）。
- **经验**：测试手段要尽量不改用户环境；必须改时集中到一个可重复的脚本。
- **出处**：`terminal-prototype:DEVELOPMENT_STATUS.md`「未做」；记忆 terminal-sidecar-hooks。

## 设计取舍与用户反馈

### 97. 「去掉」就是删掉
- **现象**：用户说 minimap 常驻很丑、状态要移到行尾，第一轮只是调淡调小，元素还在原位。用户再次强调「去掉」「放到后面」。
- **发现方式**：视觉评审。
- **原因**：用户评判的是占地和视觉重量，不是颜色深浅。
- **解决**：改 DOM 结构和盒模型：删节点、改 grid 列、改定位。改完截图确认元素真的不在原位。
- **经验**：布局反馈改结构，不改 color、opacity、font-size。
- **出处**：记忆 design-feedback-remove-not-soften。

### 98. 会话的粒度
- **现象**：界面把首条请求当会话大标题，平铺 975 条观察。
- **发现方式**：用户指出「会话应该是某个 session」。
- **原因**：没有按「会话 → 回合 → 过程」分层。
- **解决**：改为会话下的回合，回合下的过程。首条请求只标作「首条提问」。
- **经验**：先和用户对齐最基本的单位。
- **出处**：`DEVELOPMENT_LOG`「Session／turn 粒度修正（2026-09-06）」。

### 99. 「只显示一轮」改为连续滚动
- **现象**：多回合卡片 → 默认只显示一个回合 → 用户要求全会话连续滚动。
- **发现方式**：用户连续几轮反馈。
- **原因**：只显示一轮时，读者要靠目录切换，读不到上下文。
- **解决**：最新回合在上，旧回合在下，目录用来定位。终端版因屏幕小，改回一屏一轮，用 `[` `]` 和目录切换。
- **经验**：同一规则在不同屏幕尺寸下可以不同，但每次改变都要记清原因。
- **出处**：`archived/IMPLEMENTATION_SPEC.md`（2026-09-06、09-07）；`docs/TERMINAL_DESIGN.md` 第 2 节。

### 100. minimap 的来回
- **现象**：minimap 先改悬浮自动隐藏，后又恢复常驻并重新编码，最后被章节视图和回合目录替代。
- **发现方式**：原型 v4–v8 的多轮评审。
- **原因**：常驻占地；隐藏后又难以发现位置。
- **解决**：v8 恢复常驻，「刻度长度 = action 量」，取消扫光脉冲；之后 VS Code 版用细目录，终端版用 `t` 目录。
- **经验**：可视化编码要说清它代表什么，否则会被反复推翻。
- **出处**：记忆 tickbird-prototype-line；`docs/VISION.md` 开头的现状说明。

### 101. 不为不存在的规模设计
- **现象**：曾考虑「200 轮」的会话界面。
- **发现方式**：本机真实语料统计。
- **原因**：真实会话的轮数中位数 6、p90 22、最大 29。
- **解决**：首要让少量刻度清楚、安静；极端压缩只作兜底。
- **经验**：用真实分布决定设计重点。
- **出处**：记忆 turn-semantics-cross-harness；`docs/VISION.md`「Turn Minimap」。

### 102. 状态词用 Agent 自己的说法
- **现象**：「观察中」「接收中」「进行中」等自造状态词，和 Agent 界面不一致。
- **发现方式**：调研两个 Agent 的 loading 文案与用户反馈。
- **原因**：Claude Code 每轮随机取一个俏皮动词，时长格式 `12s`、`1m 33s`；Codex 显示 `Working`。
- **解决**：删除自造状态词。运行中用 Agent 原版的动词和时长格式；结束的轮次收成 `✻ Crunched for 3m 12s · 42 calls` 或 `Worked for …`。
- **经验**：旁观者用被观察者的语言，读者不用切换。
- **出处**：`DEVELOPMENT_LOG` 2026-09-23（二）（五）（六）（七）。

### 103. 请求里的 `[Image #N]` 保持原文
- **现象**：曾把 `[Image #N]` 改成可点的标签。
- **发现方式**：用户意见。
- **原因**：改写后和用户在 Agent 里看到的原文不一致。
- **解决**：撤回，保持原文；请求卡片统一用「展开全文」在编辑器区打开完整请求与原尺寸截图。
- **经验**：用户自己的话不改写。
- **出处**：0c9667d；`DEVELOPMENT_LOG` 2026-09-23（七）。

### 104. 先做原型验证可行，再提取共用逻辑
- **现象**：终端版的分屏、绑定、改绑能否成立还不知道。
- **发现方式**：规划终端版时，采纳 Codex 的建议。
- **原因**：不确定的部分直接做正式版，返工成本高。
- **解决**：先在 `terminal-prototype` 分支做原型，验证后归档；正式版只保留已验证的串联部分，并在 core 和状态插件之上重做。
- **经验**：先用最小原型回答「能不能」，再回答「怎么做好」。
- **出处**：a3a65e4；`DEVELOPMENT_LOG`「下一阶段计划」。

### 105. 设计稿导出的主题变量有坏值
- **现象**：两套深色主题的部分变量导出成了自引用 `var(--raise-N)`。
- **发现方式**：原型整理时发现。
- **原因**：导出工具的问题，两套浅色正常。
- **解决**：记录在案，移植前重新导出。
- **经验**：导出的设计变量要检查自引用和空值。
- **出处**：记忆 tickbird-prototype-line。

### 106. 去掉一个事件来源，默认它存在的代码会悄悄失效
- **现象**：精简 hook 时去掉了 `UserPromptSubmit` 和 `Stop`。单元测试先失败在「空闲时不保留显示文字」上。
- **发现方式**：C2-5 改代码后运行单元测试，读失败原因。
- **原因**：折叠状态时，会话「空闲」就丢掉显示文字，用来挡住一轮结束后迟到的片段。没有 prompt 事件以后，会话从开始起一直是空闲，所有提前显示的文字都会被丢掉。
- **解决**：不再按空闲判断，改由会话记录决定：出现同样的文字，或出现比它晚 1 秒以上的记录，就丢弃。
- **经验**：删掉一个信号之前，先找出所有用到它推出来的状态的地方，包括那些「顺便」靠它的保护逻辑。
- **出处**：`docs/TERMINAL_PLAN.md` C2-5「实现」「结果」；2026-10-08。

## 维护

每一步端到端测试后，把新发现补进对应主题，再检查「通用规律」是否要加条目或引用。

新增条目：

1. 放进最合适的主题，编号接着全文最后一个号往下排，不重排旧编号。
2. 用下面的模板。每句尽量 40 字以内，一句一个意思。
3. 出处写提交号、文档和小节，或记忆笔记的文件名，以及日期。
4. 不写密钥、账户信息、邮箱和真实会话 ID。人只写角色，路径用 `~`。

```markdown
### N. <简短标题>
- **现象**：看到了什么
- **发现方式**：端到端测试 / 用户审阅 / 单测 / 调研
- **原因**：根本原因
- **解决**：修复或决定
- **经验**：可以复用的教训
- **出处**：提交号 / 文档小节 / 记忆笔记；日期
```

结论被新版本推翻时，不删旧条目：在旧条目的「经验」里注明被哪一条推翻，再新增一条。
